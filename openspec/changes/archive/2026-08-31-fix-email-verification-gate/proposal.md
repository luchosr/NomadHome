# Proposal: fix-email-verification-gate

## Why

The email-verification gate is applied inconsistently across the platform, and in one path it is missing entirely (GitHub issue #84).

1. `POST /me/become-host` (`apps/api/src/services/auth.service.ts:257-258`) correctly throws `EmailNotVerifiedError` for a guest with `emailVerifiedAt === null`, and `apps/api/src/controllers/auth.controller.ts:162-165` maps it to a `403`. But the response body is `{ error: t("identity.become_host.email_not_verified") }` — a translated, locale-dependent string with no stable machine-readable code. This is inconsistent with the codebase's own convention: `SELF_BOOKING_NOT_ALLOWED` in `apps/api/src/controllers/booking.controller.ts:111` returns `{ error: "SELF_BOOKING_NOT_ALLOWED", message: t(...) }`, where `error` is a stable code the frontend can branch on and `message` is the display string. Because `become-host` doesn't follow this convention, the frontend (`apps/web/src/pages/BecomeHostPage.tsx:28-34`) can only branch on HTTP status: it checks for `409` (already a host) but has no way to distinguish a `403` email-not-verified response from any other `403`, so it falls through to a generic `t("error.generic.unexpected")` message. The user sees "Something went wrong" instead of being told to verify their email.

2. `BookingService.create` (`apps/api/src/services/booking.service.ts`, lines ~84-99) never checks `emailVerifiedAt` before creating a booking, and `PaymentService.createCheckoutSession` (`apps/api/src/services/payment.service.ts`) never checks it either. An unverified account can freely book a listing and pay for it. This directly contradicts `openspec/specs/booking/spec.md:104`, whose "Guest creates a booking for an available published listing" scenario already assumes `Given an authenticated guest (email verified)` as a precondition — the spec describes a guarantee the code does not enforce. Correspondingly, `apps/web/src/pages/BookingFormPage.tsx` (lines 94-105) only branches on `422` (`booking.error.overlap`, `booking.error.self_booking`); an unverified guest who reaches this bug today gets no dedicated message on the frontend either, because the backend gate does not exist to trigger one.

## What

- Add a stable, machine-readable error code to the `become-host` `403` response, following the existing `{ error: <STABLE_CODE>, message: t(...) }` convention already used by `SELF_BOOKING_NOT_ALLOWED`. Proposed code: `EMAIL_NOT_VERIFIED`.
- Add an `emailVerifiedAt` check to `BookingService.create`, thrown as the existing `EmailNotVerifiedError` (or an equivalent booking-scoped error reusing the same stable code), before any other booking precondition is evaluated. This is the single enforcement point for the guest-side email-verification gate on the booking flow — `PaymentService.createCheckoutSession` is intentionally **not** given a duplicate check, since it only ever acts on bookings that already exist, and any such booking would already have been blocked at creation time by this gate. Duplicating the check there would add a second source of truth for no additional protection.
- Update `apps/web/src/pages/BecomeHostPage.tsx` to branch on the new `EMAIL_NOT_VERIFIED` code (in addition to the existing `409` handling) and show a clear, actionable message instead of the generic fallback.
- Update `apps/web/src/pages/BookingFormPage.tsx` to branch on the same `EMAIL_NOT_VERIFIED` code returned from `POST /bookings` and show the same clear, actionable message instead of the generic fallback.

## Impact

- **Capabilities affected**: `identity` (stable error code on the existing `become-host` requirement), `booking` (new enforcement of the already-documented "email verified" precondition on booking creation).
- **Breaking changes**: No. Already-verified users are unaffected on both paths. This only blocks a previously-unintended bypass: an unverified guest can currently create a booking and pay for it, which will no longer be possible. No documented or intended behavior is being removed — the booking spec already assumed this precondition.
- **Migration required**: No. No data backfill is needed; this is MVP with no requirement to retroactively flag or void past bookings created by unverified accounts before this fix ships.
- **Out of scope**: Adding an `emailVerifiedAt` check to `PaymentService.createCheckoutSession` (deliberately not duplicated — see What). Any change to the email-verification flow itself (token issuance, resend, expiry). Any UI for guests to verify their email from within the booking or become-host flows beyond showing the new error message (e.g., an inline "resend verification email" action) — that is a candidate for a follow-up ticket, not this fix.

## Risks & Mitigations

| Risk                                                                                                                                                                                                                                                 | Likelihood | Mitigation                                                                                                                                                                               |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Existing unverified-but-already-has-bookings accounts (created before this fix, if any exist in production data) get blocked from creating _new_ bookings, which is the intended behavior but could surprise a support agent investigating a ticket. | Low        | Document the new `EMAIL_NOT_VERIFIED` code and its meaning in the delta spec so it's discoverable; no code change needed beyond the spec itself.                                         |
| Introducing a new stable error code without matching it exactly to the frontend's expected literal causes a silent regression (frontend falls back to generic message again).                                                                        | Low        | Delta spec will pin the literal string `EMAIL_NOT_VERIFIED` as the contract between backend and frontend; QA writes a red test asserting the exact response shape before implementation. |
| Reusing `EmailNotVerifiedError` across two unrelated service boundaries (auth vs. booking) couples them if one later needs a different message or code.                                                                                              | Low        | Delta spec review during Gate 2 will confirm whether to share the error class or introduce a booking-scoped one; both map to the same `EMAIL_NOT_VERIFIED` wire code either way.         |

## Rollout

Big bang, behind the normal PR/CI gate — no feature flag needed. This is a bug fix restoring already-documented intended behavior (the booking spec's "email verified" precondition), not new user-facing functionality, so there is no phased rollout concern.
